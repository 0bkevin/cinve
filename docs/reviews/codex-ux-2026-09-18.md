# Codex UX evaluation — 2026-09-18

Tested Codex CLI/app-server 0.155.0 with fresh conversations outside this
repository, using the public Cinve installation guide and production MCP.
Removed Cinve's saved server entry and its user-level instruction section first.
There were no saved Cinve OAuth credentials or local cinema sessions. Other
MCP servers were preserved. No real cinema credentials were supplied.

| Prompt / scenario | Observed behavior |

## Synthetic account end-to-end checks

The repeatable `npm run test:codex-auth` check starts an isolated PostgreSQL
cluster and local hosted server with a synthetic cinema authenticator. It uses
an ephemeral Codex app-server thread and a temporary MCP name passed through
CLI overrides. It removes test credentials and the database afterward. It does
not invoke a model or connect to a real cinema account.

Observed and verified:

- Browser approval successfully completes the installed Codex CLI's real
  OAuth callback and token exchange.
- The private cinema form saves the synthetic provider session.
- CLI authorization does **not** update an already-running anonymous Codex
  transport. Even retrying `connect_account` still failed to return a cinema link.
- `config/mcpServer/reload` makes the existing thread recognize the authorized
  client and connected cinema.
- Native `mcpServer/oauth/login`, with the thread ID, emits a successful completion
  notification and makes `connect_account` work in that same thread without a
  separate refresh.
- Codex's CLI callback returns HTTP 400 for the standard OAuth denial redirect
  and leaves the login command waiting. The test stops that pending process.
  This is a client limitation, not successful cancellation completion.

## Changes made from these findings

- The installation guide registers anonymous Codex access by editing only the
  Cinve TOML table; it no longer recommends the auto-authorizing `mcp add` path.
- `get_auth_status` identifies whether the calling assistant is authorized,
  independently of cinema-session state. Anonymous provider statuses are now
  `client_authorization_required`, not the misleading `missing`.
- Shared instructions prefer native authorization, keep the browser callback
  alive, show its URL promptly, watch completion, stop cancelled attempts,
  and refresh once after CLI authorization instead of repeating login.
- Assistants must not invent native host tools. Where a host exposes neither
  native login nor connection refresh, a user reconnect remains necessary.

## Limits

No real cinema-account login or private ticket-price query was performed.
Browser layout was not visually reviewed; forms and callbacks were exercised
through HTTP. The native app-server integration works, but a remote MCP cannot
force every host UI to expose or invoke those native client actions. These
results do not establish a universal zero-reconnect experience.
